### Clarifications

#### Round 1

**How should `make publish` log in to Docker Hub (account iomega)?** _(Hub login)_

- [x] **Token in .env (Recommended)** – Add DOCKERHUB_USERNAME=iomega and DOCKERHUB_TOKEN (an access token, not your password). publish runs `docker login --password-stdin`. Works without prompts.
- [ ] Interactive docker login once – You run `docker login` yourself; publish only tags and pushes.

**Which tags are pushed for api, mcp and web?** _(Tags)_

- [x] **Version + latest (Recommended)** – iomega/netcore-rag-api:0.9.1 and :latest (same for mcp and web). EC2 deploys the pinned version.
- [ ] Version only – Immutable tags only.
- [ ] Version + git SHA – Adds a :<short-sha> tag for traceability.

**.env names the secret key AWS_ACCESS_SECRET, but Terraform and AWS tools expect AWS_SECRET_ACCESS_KEY. How should we handle that?** _(AWS secret)_

- [ ] Map it in the Makefile (Recommended) – iac targets export AWS_SECRET_ACCESS_KEY=$(AWS_ACCESS_SECRET). Your .env stays as it is.
- [x] **Rename it in .env** – Use the standard name. I'd update .env and .env.example.

**Instance size? Measured idle use is about 380 MiB, but an agent run, an image pull and the OS add more, and t3.micro has 1 GiB.** _(Instance)_

- [ ] t3.micro + 2 GiB swap (Recommended) – Your choice, made safer with a swap file and memory limits per container. Free-tier eligible. May be slow under load.
- [x] **t3.small (2 GiB)** – More headroom; about twice the cost.
- [ ] Variable, default t3.micro – instance_type is a Terraform variable you can change later.

#### Round 2

**How do the app secrets in .env (OpenAI key, API_KEYS, Jira token) reach the EC2 instance?** _(Secrets)_

- [x] **Copy .env over SSH (Recommended)** – After the instance is up, Terraform uploads .env to /opt/netcore/.env (chmod 600). Only the file path goes into Terraform state, not the values.
- [ ] SSM Parameter Store – Each secret becomes a SecureString; an instance role reads them at boot. Most secure, but adds IAM resources and work.
- [ ] user_data template – Simplest, but the secrets end up in Terraform state and in the instance metadata.

**On the new server Chroma starts empty. How does the knowledge base get there?** _(KB data)_

- [x] **Copy the local Chroma volume (Recommended)** – make exports the chroma-data volume to a tar file, uploads it and restores it before start-up. No OpenAI cost, and you get exactly your current data, access levels included.
- [ ] Populate remotely through an SSH tunnel – Runs populate locally against the remote Chroma. Costs OpenAI embedding and description calls.
- [ ] Leave it empty – You populate it yourself later.

**Which inbound ports should the security group open?** _(Ports)_

- [x] **22 from my IP + 80 to all (Recommended)** – SSH only from your detected public IP. The web UI on 80 is public. API 8080, MCP 9090 (no auth!) and the databases stay closed (use SSH tunnels).
- [ ] 22 + 80 to all – SSH open to the whole internet (password login is off; key only).
- [ ] 22 only – Reach everything through SSH tunnels.
- [ ] 22, 80, 8080 to all – Also exposes the API and /docs publicly.

**Which OS and Docker?** _(OS)_

- [x] **Ubuntu 24.04 + Docker CE (Recommended)** – Official Canonical AMI (looked up at apply time); docker-ce and the compose plugin from Docker's apt repository, as you asked.
- [ ] Amazon Linux 2023 – Uses Amazon's docker package (not Docker CE); the compose plugin is installed by hand.

#### Round 3

**How is the new SSH key pair generated?** _(Key pair)_

- [x] **Terraform tls_private_key (Recommended)** – ED25519 key generated by Terraform, registered as an aws_key_pair, and saved to iac/.keys/netcore-ec2.pem (git-ignored, 0600). The private key is also in the (local, git-ignored) state.
- [ ] ssh-keygen in a make target – Generated locally; Terraform uploads only the public key, so the private key never enters state.

**How is the stack deployed on the instance?** _(Deploy)_

- [x] **All in terraform apply (Recommended)** – cloud-init installs Docker CE and swap. A null_resource (SSH) uploads the compose file, .env and the Chroma snapshot, then pulls and starts. It re-runs when the version or the files change.
- [ ] Terraform infra + make iac-deploy – Terraform builds only the server; a separate make target (scp/ssh) deploys and updates the app.

**Which compose file runs on EC2?** _(Compose)_

- [x] **iac/compose.prod.yaml (Recommended)** – iomega/\* images from Docker Hub, no builds, only web:80 published (api, mcp and the DBs internal), memory limits, restart policies.
- [ ] compose.yaml + override – Reuses the dev compose with an override file that swaps images and unpublishes ports.

**Network, IP, disk and Terraform state?** _(Infra)_

- [x] **Default VPC, EIP, 30 GiB, local state (Recommended)** – Default VPC and subnet, an Elastic IP (stable across stop/start), 30 GiB gp3 encrypted root, state in iac/ (git-ignored).
- [ ] New VPC + S3 state – Dedicated VPC and subnet, remote state in S3 with locking. More production-like, more resources.
- [ ] Default VPC, no EIP – The public IP changes after a stop/start.

#### Round 4

**Make target names?** _(Targets)_

- [x] **publish + iac-\* (Recommended)** – publish; iac-init, iac-plan, iac-up (apply), iac-ssh, iac-output, iac-down (destroy). They appear in the TUI with tags ([cost] / [danger]).
- [ ] publish + deploy / undeploy – Fewer, broader names.

**Release version?** _(Version)_

- [x] **0.10.0 everywhere (Recommended)** – API, web and MCP versions plus image tags 0.10.0; CHANGELOG [0.10.0].
- [ ] Keep 0.9.x – Publish the current 0.9.0 images; CHANGELOG under 0.9.1.

**How far should I verify against real AWS? Applying creates billable resources.** _(Live test)_

- [x] **Apply, test, keep running (Recommended)** – terraform apply, then check the web UI over the public IP, SSH and container health. It stays up for you (make iac-down to remove it).
- [ ] Apply, test, then destroy – Proves it end to end, then removes everything.
- [ ] Validate + plan only – No AWS resources created; you run make iac-up yourself.

**Also publish now to Docker Hub as part of verification?** _(Push now)_

- [ ] Yes, after you add the token (Recommended) – I stop and ask you to put DOCKERHUB_TOKEN in .env, then run make publish (images become public on hub.docker.com/u/iomega).
- [ ] No, I'll run publish myself – I only dry-run it.
- [x] **Other:** "I have already added DOCKERHUB_TOKEN to .env."

Deployed live to http://13.202.254.140/ with all six containers healthy and left running; `make iac-down` removes it.
